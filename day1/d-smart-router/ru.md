## Условие

Адильхан и Дархан разрабатывают систему защиты персональных данных. Перед обработкой документов
система маскирует имена, телефоны, адреса и другие персональные данные с помощью набора правил и
модели распознавания именованных сущностей (NER). Иногда система пропускает персональные данные.
Для дополнительной проверки можно использовать большую языковую модель, но бюджета хватает только
на **10 % документов**.

Разработайте **роутер**: для каждого документа выдайте **оценку риска** — одно конечное число,
тем большее, чем выше приоритет дополнительной проверки. На проверку уходят документы с
наибольшими оценками. Чем больше документов с пропусками попадёт в выбранные 10 %, тем лучше;
особое внимание — **критическим** персональным данным.

Исправлять маскирование не нужно, требуется только расставить приоритеты.

### Категории

| Класс | Что включает |
|---|---|
| `USER` | имя, фамилия, имя пользователя |
| `ADDR` | страна, город, область, район, улица с домом, индекс, координаты |
| `MAIL` | адрес электронной почты |
| `TEL` | номер телефона, номер факса |
| `IBAN` | номер счёта, IBAN, SWIFT/BIC, routing-номер |
| `DOC` | номер лицензии, сертификата, медкарты, полиса |
| `CARD` | номер банковской карты, CVV |
| `IIN` | ИИН, иной национальный идентификатор, налоговый номер |

Близкие типы данных объединены в один класс для простоты. **Критические классы:** `IIN`, `CARD`,
`TEL`, `MAIL`, `IBAN`. Из `has_critical_leak = 1` следует `has_leak = 1`.

**Пропуск** — сущность, не покрытая масками целиком (полностью или частично осталась в тексте).

## Формат входных данных

JSON Lines, UTF-8, один объект в строке.

| Поле | Описание |
|---|---|
| `document_id` | идентификатор документа |
| `lang` | `ru`, `kk`, `en` или `mixed` |
| `text` | исходный текст |
| `masked_text` | текст после маскирования: каждая найденная сущность заменена на `[КЛАСС]` |
| `cascade_entities` | **что нашла система маскирования**: массив объектов со `start`, `end` (символьные смещения в `text`, полуинтервал), `type` (класс), `source` (`"rule"` или `"ner"`), `confidence` (уверенность NER или `null` для правил) |
| `pii` | **эталонная разметка** со `start`, `end`, `label` — только в `train.jsonl` |
| `has_leak`, `has_critical_leak` | метки 0/1 — только в `train.jsonl` |

**Не путайте два массива:** `cascade_entities` — предсказания системы, их ошибки и требуется
предсказывать; `pii` — эталон, в тестовой выборке его нет.

## Формат выходных данных

`predictions.csv` в UTF-8, с заголовком:

```
document_id,risk_score
39703d9ea01c9e58,0.871
1a2b3c4d5e6f7890,0.014
```

Ровно одна строка на каждый документ теста, без повторов и неизвестных идентификаторов.
`risk_score` — конечное число (разделитель — точка), `NaN` и `Inf` не допускаются. Оценка не
обязана быть вероятностью: важен только порядок. Порядок строк произвольный.

Файл, не соответствующий формату, получает **0 баллов**.

## Примеры

Две строки входного файла (тексты сокращены):

```
{"document_id": "a1", "lang": "ru", "text": "Клиент Айгерим Сапарова, тел. +7 701 000 00 00.", "masked_text": "Клиент [USER], тел. [TEL].", "cascade_entities": [{"start": 7, "end": 23, "type": "USER", "source": "ner", "confidence": 0.97}, {"start": 30, "end": 46, "type": "TEL", "source": "rule", "confidence": null}]}
{"document_id": "a2", "lang": "kk", "text": "Байланыс: aigerim [at] mail [dot] kz, ЖСН 000000000000.", "masked_text": "Байланыс: aigerim [at] mail [dot] kz, ЖСН [IIN].", "cascade_entities": [{"start": 42, "end": 54, "type": "IIN", "source": "rule", "confidence": null}]}
```

Ответ:

```
document_id,risk_score
a1,0.05
a2,0.93
```

В `a2` адрес почты записан словами (`[at]`, `[dot]`), правило его не распознало, и в
замаскированном тексте он остался — это критический пропуск. В `a1` всё замаскировано.
Пример показывает только формат, правильность оценок в нём не проверяется.

## Примечания

**Отбор документов.** При N документах в тесте на проверку идут `K = floor(0.1 × N)` документов с
наибольшими оценками; при N = 15 001 это K = 1 500. При равных оценках документы упорядочиваются
по возрастанию `document_id` как строк.

**Public / private.** Балл во время тура считается на 30 % тестовой выборки, итоговый — на
оставшихся 70 % и объявляется после тура. Они могут заметно различаться.

---

## Система оценки

Обозначим: **A** — документы теста с `has_leak = 1`, **C** — с `has_critical_leak = 1`,
**S** — выбранные роутером верхние K документов. Запись `|X|` — количество документов,
`∩` — пересечение.

```
R_all      = |S ∩ A| / |A|
R_critical = |S ∩ C| / |C|
score      = 100 × (0.5 × R_all + 0.5 × R_critical)
```

Оба показателя считаются на одном и том же множестве S — отдельного бюджета на критические
пропуски нет. Документ учитывается один раз в каждом показателе независимо от числа пропущенных
в нём сущностей. Максимальный балл — 100.

**Пример.** В тесте 10 000 документов, на проверку идёт 1 000. Всего 200 документов с пропусками,
из них 40 с критическими. Среди выбранных оказалось 140 с пропусками и 20 с критическими:

```
R_all      = 140 / 200 = 0.70
R_critical =  20 /  40 = 0.50
score      = 100 × (0.5 × 0.70 + 0.5 × 0.50) = 60
```

**Ограничение на посылки.** По каждой задаче можно отправлять не более одной посылки в минуту.
