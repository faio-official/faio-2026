## Легенда

**Команда локализации** крупной телеком-компании выбирает систему машинного перевода для поддержки клиентов в паре казахский$\leftrightarrow$русский. Чтобы определить победителя, команда провела слепую оценку с участием людей: для каждого исходного предложения две конкурирующие системы выдавали свой перевод, оба варианта показывались рядом как **A** и **B**, а человек-лингвист решал, какой из них лучше — или что не годится ни один.

Всю эту работу выполнили два лингвиста. Назовём их **person1** и **person2**. Они работали по одной и той же инструкции и на одном и том же материале, но по мере поступления результатов руководитель команды заметил неприятную вещь: судят они *по-разному*. Одна и та же пара переводов могла вызвать у одного лишь лёгкое недовольство, а у другого — полное отклонение. Там, где один лингвист видел два приемлемых варианта, другой видел две неудачи.

Прежде чем компания потратит годовой бюджет на систему-победителя, руководитель хочет понять, какая часть вердикта определяется самим переводом, а какая — человеком, который этот вердикт поставил. И на пути стоит практическая проблема: при переносе платформы оценивания часть журнала была повреждена, и для большого блока суждений **колонка с именем того, кто их вынес, была утрачена**.

Сохранившиеся записи лежат в `train.csv`. Повреждённые — в `test.csv`. Ваша задача — восстановить утраченную атрибуцию: для каждого суждения из повреждённого блока определить, кто его вынес.

## Формальная постановка задачи

Каждая строка данных — это **одно человеческое суждение об одной паре переводов**. Она содержит исходное предложение, эталонный перевод, два конкурирующих перевода, показанных как A и B, и вердикт, который поставил лингвист: какую сторону он предпочёл и какую оценку качества выставил каждой из них. Какие именно системы произвели эти два перевода, не раскрывается.

- `train.csv`: суждения с сохранившейся колонкой `annotator` (`person1` или `person2`).
- `test.csv`: суждения, у которых колонка `annotator` удалена. Для каждой строки нужно оценить вероятность того, что это суждение вынес `person2`.

Оба лингвиста вынесли одинаковое количество суждений — как в обучающей, так и в тестовой выборке.

## Входные данные

Файлы `train.csv` и `test.csv` содержат следующие общие колонки.

- `id` — идентификатор строки.
- `direction` — направление перевода: `kk->ru` или `ru->kk`.
- `original` — исходное предложение.
- `reference` — эталонный перевод исходного предложения, выполненный человеком.
- `translation_1` — перевод, показанный лингвисту как **A**.
- `translation_2` — перевод, показанный лингвисту как **B**.
- `preference` — вердикт. Одно из значений:
  - `a` — перевод A лучше;
  - `b` — перевод B лучше;
  - `tie` — оба перевода равного качества;
  - `both_bad` — ни один из переводов неприемлем.
- `rating_a`, `rating_b` — оценка качества, которую лингвист выставил переводу A и переводу B, по шкале `0`, `1`, `2`, где `2` — лучшая. Небольшая часть этих значений отсутствует.

В `train.csv` есть одна дополнительная колонка:

- `annotator` — `person1` или `person2`, лингвист, вынесший суждение. Это целевая переменная.

## Выходные данные

Участники должны отправить только один CSV-файл с именем **solution.csv** следующего формата:

```
id,probability
0,0.83
1,0.12
2,0.50
...
```

`probability` — ваша оценка вероятности (вещественное число на отрезке $[0, 1]$) того, что суждение в данной строке вынес **person2**. Значение, близкое к $1$, означает уверенность в том, что это `person2`; значение, близкое к $0$, — уверенность в том, что это `person1`.

**Важно:** отправляйте только файл `solution.csv`. Исходный код не требуется. Файл должен содержать ровно одну строку для каждой строки `test.csv`, а порядок значений `id` в `solution.csv` должен строго соответствовать порядку в `test.csv`, начиная с `0` и до максимального идентификатора.

## Оценивание

- Ваши предсказания оцениваются метрикой **ROC-AUC** (площадь под ROC-кривой), вычисляемой с `person2` в качестве положительного класса.
- ROC-AUC измеряет то, насколько хорошо ваши вероятности *ранжируют* строки, а не то, попадают ли они по какую-то сторону от порога. Отправлять только значения $0$ и $1$ допустимо, но при этом теряется вся информация о вашей уверенности.
- Решение, присваивающее всем строкам одно и то же значение, получает ROC-AUC ровно $0{,}5$.
- Итоговый балл — это ROC-AUC, приведённый к шкале $0$–$100$ и округлённый до двух знаков после запятой: $$\text{балл} = \text{ROC-AUC} \times 100$$
- Решение, которое не удаётся прочитать, отклоняется как ошибка формата и не получает балла. Это происходит, если количество строк не совпадает с `test.csv`, если значения `id` идут не в том же порядке, что и в `test.csv`, если колонка `probability` отсутствует или названа иначе, а также если какое-либо значение пустое, не является числом или выходит за пределы отрезка $[0, 1]$.

## Пример

**Вход (`train.csv`), одна строка, по колонкам:**

```
id           : 0
direction    : ru->kk
original     : Спокойной ночи, до завтра.
reference    : Қайырлы түн, ертеңге дейін.
translation_1: Қайырлы түн, ертеңкеге дейін.
translation_2: Қайырлы түн, ертеңге дейін.
preference   : b
rating_a     : 0
rating_b     : 2
annotator    : person1
```

**Вход (`test.csv`):** те же колонки, без `annotator`.

**Ваш ответ (`solution.csv`):**

```
id,probability
0,0.83
1,0.12
2,0.50
```
